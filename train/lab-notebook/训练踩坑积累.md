# 训练踩坑积累（跨轮次归档，新坑持续追加）

每条：现象 → 根因 → **为什么没提前发现** → 防再犯。目的是同类错误只犯一次。

---

## 1. SFT 崩溃：transformers 5.20 的 tokenizer.pad 不处理 labels 键（2026-10-24）

- **现象**：train_sft.py 首次真实执行，两次都在 30 秒内崩：`Unable to create tensor ... excessive nesting` + `expected sequence of length 40 at dim 1 (got 41)`。
- **根因**：DataCollatorWithPadding 走 tokenizer.pad，base 类 `_pad` 只给 `model_input_names`（input_ids/attention_mask/token_type_ids/special_tokens_mask）补长，**labels 不在其列** → 变长样本 labels 保持原长，堆 batch 抛错。修复：自写 make_collator 右对齐 padding（input_ids 补 pad_id、labels 补 -100、attention_mask 0/1），不走库。
- **为什么没提前发现**：任务 #14 的「训练脚本冒烟」只冒了 PT——PT 用 PackedDataset 定长打包（seq 2048 全体等长），**根本没有 padding 路径**；SFT 的变长样本路径从未被真实执行过。swap 脚本里「PT 完自动接 SFT」是全自动一把梭，阶段之间没有人工门禁，SFT 第一次真实跑就是生产配置。
- **防再犯**：①冒烟必须逐条覆盖真实数据路径（定长冒烟 ≠ 变长冒烟）；②新脚本第一次跑之前，用 `--max-steps 3` 小步冒烟（train_sft.py 现已内置该参数）；③全自动链路的每个下游阶段上线前必须独立冒烟过，不能默认「上游跑通了=下游没问题」。

## 2. chunked CE 归一化三坑（2026-10-24，换班上线后逐一暴露）

自研分块 CE（手写 autograd.Function 绕 logits 显存墙）三个归一化 bug，全部是「等价自检没拦住、上线才爆」：

| 坑 | 现象 | 根因 |
|---|---|---|
| ① gas 倍 | 上线首测 loss 25.6，正确值 3.2，恰好 ×8（gas=8） | transformers v5 原生 CE 按「整个累积周期 token 数」num_items_in_batch 归一化，分块 CE 只按单 micro-batch n_tokens 归一化 |
| ② 梯度缺乘 | grad_norm 4.2 vs 正确 1.5 | backward 里 dhidden/dweight/dbias 三个梯度漏乘 grad_output |
| ③ 跨卡减半 | 双卡 loss 1.58 = 3.17/2 | average_tokens_across_devices=True 时 num_items 跨卡汇总，原生乘 loss_scale 抵消，override 的 compute_loss 漏了 |

- **为什么没提前发现**：等价自检（check_ce_ds.py）最初的设计矩阵是**单卡、lr=0、固定 gas**——恰好把三个坑的触发条件全部绕开：①需要 gas>1，②需要真实反向传播，③需要双卡。自检「通过」只证明「在被测配置下等价」，不证明「在所有生产配置下等价」。教训：**自检矩阵必须与生产逐维对齐**（卡数、gas、lr、batch 尺寸一个都不能少）。③号坑尤其典型——单卡自检永远发现不了，只有双卡环境才暴露。
- **防再犯**：①自研 loss/梯度代码的等价自检，配置矩阵 = 生产配置全集（卡数×gas×lr 非零）；②换班类脚本必须带相对基准门禁（±30%），绝对阈值拦不住倍数 bug（1.873 能过 0<loss<10）；③修完在双卡上跑探针 A（原生）vs C（生产代码 super() 直调）逐位比对。

## 3. 全链自动化的阶段间无门禁（元教训，覆盖 1+2）

- **现象**：swap_optimize.sh 一把梭「PT 完自动接 SFT」，SFT 段连着翻车两次后 watcher 静默退出，靠人查日志才发现。
- **根因**：把「首次执行的路径」放进了无人值守的自动链路。
- **防再犯**：首次执行的阶段一律先独立冒烟（小步数、快失败），冒烟通过才允许进自动链路；自动链路每一阶段完成都要有可发现的落盘标记（TRAINING_FINISHED / STATUS.txt），失败要有显式 exit 码。

## 4. PT2 冒烟连挂四次（2026-10-25 凌晨，WSD 上线）

- **现象**：PT2（seq 4096、bs16、chunked CE、WSD）冒烟四连败：①`create_scheduler` 里 `LambdaLR(None)`（AttributeError: NoneType has no param_groups）②③OOM 30GB（去掉 compile 后数值一模一样）④`NoneType has no get_last_lr`。
- **根因**：
  1. transformers 5.x `create_optimizer_and_scheduler` 调 `create_scheduler(num_training_steps=...)` **不带 optimizer 参数**，旧代码假设 optimizer 必传 → 传 None 给 LambdaLR 炸。修：`optimizer or self.optimizer`。
  2. OOM 真凶不是 compile 也不是 cudagraphs：**seq4096×bs16 无梯度检查点时，28 层为反向保存的激活累计 ~45GB**（每层 q/k/v/o/gate/up 投影输出全保存，q 是 268MB/层、gate+up 是 800MB/层）。SFT 一直默认开检查点所以从没暴露；旧注释「bs16 激活 ≈12.6GB 装得下」是按 seq2048 估的，作废。修：恢复默认梯度检查点（PT2 路线去掉 --no-grad-checkpoint）。
  3. transformers 5.x `create_scheduler` 的契约是**必须赋给 `self.lr_scheduler` 并返回**（调用方忽略返回值）。旧代码只 return 不赋值 → self.lr_scheduler 恒 None → 后续 get_last_lr 炸。修：`self.lr_scheduler = LambdaLR(...); self._created_lr_scheduler = True`。
  4. 附加发现：torch.compile 会把 chunked CE 的分块循环融合成完整 logits（seq4096×bs16×152k 词表 ≈20GB），内存墙回归。SFT 在 seq2048 能跑纯属侥幸（10GB 放得下）。PT2 路线不开 compile。
- **为什么没提前发现**：PT 冒烟（seq2048 bs4）从未在「seq4096 + bs16 + 无检查点」组合下执行过；transformers 5.x 的 API 契约变化（create_scheduler 签名/赋值语义）与训练知识里的 4.x 记忆不一致，没有逐条对着安装版本源码核过。
- **防再犯**：①新 seq-len×bs 组合必须真实冒烟（3 步足够暴露显存）；②override transformers Trainer 钩子时先读安装版本源码确认契约（传参语义、返回值语义、赋值语义）；③显存估算必须以「保存激活总量 = Σ每层投影输出」逐层算，不能拿历史 seq 线性外推。

## 5. 冒烟门禁的判定信号与调度验证（同夜补充）

- WSD 冒烟通过时输出：step1 lr=0（warmup 首步）、step2 lr=2e-4（峰值）、step3 保持峰值；loss 出数即 SMOKE_OK。正式跑 step10 lr=4.724e-06 = 2e-4×9/381，与 warmup=5%（381 步）精确吻合——**lr 数值本身就是 WSD 接线的验证信号**，冒烟日志里多看一眼 learning_rate 字段可省掉曲线后验。

## 6. sft2-watch 会话无声死亡（2026-10-26 上午，SFT2 收工后）

- **现象**：SFT2 收工（10:06:55）后 watcher 进入 convert 阶段，备份清单文件已写（说明到了 stage 2），随后整个 tmux 会话消失——无 "convert 失败" 日志、无 OOM 证据（dmesg 干净）、sft2_f16.gguf 未产出、done 标志未打。Mac 侧轮询链无心跳检测，若无人工发现会永远傻等（失败探测只 grep「两次尝试均失败/人工介入」，无声死亡不触发）。
- **根因**：未定论。证据：①watch_sft2.log 停在 "SFT2 完成"，连 convert 的 stdout 重定向都没写入 → 死点在 convert 启动前后；②其他 tmux 会话（agent/llm-synth 等）全部存活 → 非重启、非 tmux server 级故障；③dmesg 无 OOM。最可能：会话被外部动作杀掉（机器上另有 agent 会话在跑）或 convert 进程与 shell 同死于某种信号，无日志可追溯。
- **恢复**：手动补跑 convert（绝对路径、RC=0、1.5GB/311 tensors）+ touch sft2_f16.done + 恢复记录写入 watch_sft2.log（措辞避开失败探测关键词「人工介入」，写了「人工补跑」）。
- **为什么没提前发现**：watcher 的失败出口都假定「脚本活着、能写日志」；轮询链的失败探测也依赖 watcher 写失败标记。**看护进程自身死亡**这一故障模式两边都没覆盖——watcher 没心跳上报，poller 没心跳检查。
- **防再犯**：①ssh 一行流一律用绝对路径（本次 `cd && ... >> ../logs/...` 重定向相对路径没生效，教训同）；②下一版看护链加心跳：watcher 每轮循环 touch 心跳文件 + poller 检查心跳新鲜度（超 30 分钟无心跳 = 看护死亡，报警而不是傻等）；③无人值守链的每个常驻进程都要有「自己被杀掉怎么办」的答案，不能只设计成功路径与显式失败路径。

## 7. 自转 GGUF 丢失 added_tokens：聊天模板退化（2026-10-26，M1 冒烟暴露）

- **现象**：EngineKit 冒烟时发现 `tokenize("<|im_end|>", add_special=true)` 返回 6 个字面 subword token，而非特殊 token 151645；demo 生成时模型首 token 输出 `<|im_end|>` 字样且 is_eog 不触发。
- **根因**：训练机 `tools/llama_convert/gguf-py` 是老版本（vocab.py 时代），只从 `tokenizer_config.json` 的 `added_tokens_decoder` 读特殊 token；Qwen3 该字段**不存在**（config 只有 eos_token/extra_special_tokens），26 个 added tokens 全在 `tokenizer.json` → GGUF 缺 `tokenizer.ggml.added_tokens` 键。词表本体完好（151936、EOG 标志正确），坏的只是「字符串→特殊 token」的编码映射。
- **为什么没提前发现**：①PPL 类评测对 tokenizer 的特殊 token 映射不敏感（语料无 `<|im_end|>`），SFT1 全链验证走的是 PPL + 少量生成，生成部分当时未逐 token 检查模板；②旧 gguf-py 的 API 契约（读哪里的 added tokens）没对着 Qwen3 的 tokenizer 文件核过——与坑 #4「对安装版本核契约」同源。
- **修复**：①引擎侧（已做）：EngineCore 按 token ID 直拼 Qwen3 聊天格式（151644/151645），与正确模板逐 token 等价，特殊 token 在 BPE 中不参与 merge，段间无跨边界合并；②训练侧（待拍板）：用钉版 llama.cpp 自带新 gguf-py 重转 f16 → 重量化 → 生成类评测重跑。
- **防再犯**：①GGUF 产出后加一道「tokenizer 契约校验」：`tokenize("<|im_end|>", add_special=true)` 必须等于 EOT id，进评测链前先跑（一行脚本）；②任何 GGUF 接入生成链路前，先用 llama-cli 同参数对拍首 10 token，模板问题无处遁形。
