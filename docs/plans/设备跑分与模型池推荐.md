# 设备跑分与模型池推荐 · 接口契约 v0.1

> 状态：契约已定稿（2026-10-24 三开放点 + 2026-10-25 模型池定位均已拍板，见第 8 节）。纯文档，不动代码。
> 来源：用户提案「部署前给手机跑分（类鲁大师），按分数推荐模型池」+ 追加要求「不同用户之间可以相互比较（情绪价值）」。

## 1. 目标与定位

- **一句话**：首启向导的一环——用引擎真实跑一个冻结的标准负载，得出可跨用户比较的「AI 性能分」，据此推荐模型池与默认速度档。
- **双目标**：真标准（分数反映真实可用性，直接喂给 SpeedTier/内存档位）+ 情绪价值（可比、击败百分比、天梯、分享卡片）。
- **SDK 优先（2026-10-24 用户定调）**：App 开发时间过长，本项目重要用途是**开源 SDK 供别人做 App**。跑分全套能力必须是 EngineKit 的公开 API；demo App 只做薄壳参考实现（首启页 + 设备页），不承载核心逻辑。
- **跨 App 可比性红利**：同一 SDK = 同一基准，不同开发者 App 里跑出的分数天然可比，排行榜（V2）是跨 App 基础设施——SDK 优先让情绪价值覆盖面更大。
- **跑分可跳过、可重测**：不阻塞首启使用；随时在「设备」页重测。

## 2. 跑分基准（可比性的根基）

分数可比的前提是**工作量冻结**。三样东西全部锁死，任何一样变了分数就不可比：

| 项 | 契约 | 说明 |
|---|---|---|
| 基准模型 | 自训 0.6B Q4_K_M **首发版冻结** | 发布后不升级（升级 = 分数重新校准 + 天梯标注新基准版本号）。对外口径：**基于 Qwen3-0.6B 继续训练**，不称「自研」 |
| 基准 prompt | 固定中文文本（约 300 字，覆盖翻译/摘要/日程三类高频任务） | 常量写死在引擎里，不随版本改 |
| 输出规格 | 固定生成 512 tokens，采样参数固定（temp 0.8 等） | 输出量是 tok/s 的分母，必须固定 |
| 测量窗口 | 持续 2 分钟（预热 10 秒不计分） | 防「冷启动峰值刷分」，记录整条 tok/s 曲线 |
| 测试纪律 | 充电中允许跑分，但开跑前明确告知「充电发热可能导致分数偏低」；低电量（<20%）同提示；分数标注「条件不佳」；重测冷却 5 分钟 | 防刷分：分数失真会反噬成嘲讽价值 |

## 3. 分数公式 v0.1

三个子分各映射到 0-100，再加权合成「AI 性能分」（0-100 整数）：

```
速度分 S = min(100, 持续tok/s × 2)          # 50 tok/s 封顶
稳定分 T = 100 × 后半段均值tok/s / 前半段均值tok/s   # 降频越狠分越低
内存分 M = min(100, 可用内存GB × 10)        # os_proc_available_memory，10GB 封顶

AI 性能分 = round(0.6×S + 0.25×T + 0.15×M)
```

- 权重与映射系数是 v0.1 占位，**真机数据后校准**（校准流程：三台真机/双 Mac 实测 → 调整映射使分档清晰、跨代差距明显）。
- 校准只调系数，**不换基准负载**；公式版本号随系数发布，天梯分数标注公式版本。

## 4. 档位映射 → 推荐模型池

分数分三档（阈值 v0.1 占位，随校准调整）：

| 档位 | 分数 | 推荐模型池（GGUF） | 默认 SpeedTier |
|---|---|---|---|
| 旗舰 | ≥80 | 4B Q4_K_M + 1.7B Q8_0 + 0.6B Q8_0 | 极速 |
| 主流 | 55-79 | 1.7B Q4_K_M + 0.6B Q8_0 | 均衡 |
| 入门 | <55 | 0.6B Q4_K_M | 节能 |

> 上表是远期全量池（4B/1.7B 后置）；**首发只有 0.6B，按 §4.1 清单执行**。

- 推荐池只给建议，用户仍可一键换任意已发布模型（落地计划「一键换模型」约束不变）。
- SpeedTier 四档用户始终可手动调，跑分只定默认值。

### 4.1 首发模型池清单（0.6B，2026-10-25 拍板，2026-10-26 更新为 SFT3B 最终版）

模型池分两层：**推荐池**（咱的最终版，跑分推荐唯一来源）+ **可选池**（官方原版，仅开放下载）。

**推荐池（咱的最终版 SFT3B 四档，实测数据见用户指南）：**

| 档位 | 大小 | 定位 |
|---|---|---|
| F16 | 1.5 GB | 质量款——不量化原模型，内存富余设备（≥8GB）追极致用 |
| **Q5_K_M ⭐ 旗舰款** | 551 MB | **默认推荐**：工具调用 40/40 发射 + 15/15 日常题全过，比 F16 省 63% 体积且更快 |
| Q4_K_M | 484 MB | 省内存款——6GB 设备的稳妥选择 |
| IQ4_XS | 450 MB | 最小款——imatrix 加持，体积最小、质量仍超 Q4_K_M |

**可选池（官方原版 Qwen3-0.6B 的 Q8_0 / Q5_K_M / Q4_K_M）：**

- 开放下载（开源模型，用户有选择权），但**不参与推荐**——实测日常任务表现不稳（RED 判定、思考链复读），只作开源对照参考。
- 用户指南里明确标注「官方原版，不推荐日常使用」。

### 4.2 速度增强策略：投机采样（提案，待实测拍板）

> 来源：MiniCPM-V 4.7 三件套之一（DSpark 投机采样）；用户 2026-10-25 提案「设备性能足够时，旗舰款换成投机采样」。

- **机制**：草稿模型快速生成候选 token，主模型一次批量验证，猜对的保留——把固定开销摊到多个 token。llama.cpp 原生支持（`--model-draft`），同架构草稿共享 KV cache，无需自研。
- **收益公式**：加速比 ≈ (γ+1) / (1 + γ × 草稿耗时/主模型耗时)。草稿必须显著快于主模型才划算。
- **0.6B 实测（2026-10-26 Mac 预筛已判死，见下文实测表）**：IQ4_XS 草稿 + Q5_K_M 主，草稿仅快 1.25 倍 → 实测慢 2.2-5.8×——首发不默认开。
- **4B 才是主战场**：4B 主 + 0.6B 草稿（快 5-7 倍）→ 预估 2 倍+，4B 上线时投机采样为标配。
- **落地形态**：SpeedTier「极速」档预留加速策略挂载点；跑分高的设备默认推荐「主模型 + 草稿」组合，跑分低的不推荐（内存不足）。
- **拍板规则（两级，2026-10-25 用户定调「咱主要是手机端实测」）**：
  1. **Mac 预筛**：SFT2 评测链跑完后，Mac 实测 Q5_K_M 主 + IQ4_XS 草稿的接受率与加速比。Mac 上 <15% 直接判死（手机内存带宽瓶颈更重，只会更差）。
  2. **真机终裁**：Mac 预筛可观（≥25%）才值得上真机——随 M2 EngineKit 首版上 iPhone 18 Pro Max，与跑分校准（三台真机/双 Mac）同批实测；真机数据定 0.6B 开不开、4B 怎么配。

- **Mac 预筛结果（2026-10-26 实测，SFT3B Q5_K_M 主 + IQ4_XS 草稿，M5，temp 0.8，512 tokens，llama-speculative-simple）**：

  | 配置 | 接受率 | 总耗时 | 相对基线 |
  |---|---|---|---|
  | 基线（Q5_K_M 单跑 163.9 t/s） | — | 3.12s | 1× |
  | 草稿单跑（IQ4_XS 205.6 t/s） | — | — | 快 1.25× |
  | n_max=4 | 40.3% | 6.92s | 慢 2.2× |
  | n_max=8 | 25.3% | 11.08s | 慢 3.6× |
  | n_max=16 | 13.7% | 18.19s | 慢 5.8× |

  **判死（0.6B 同尺寸投机采样）**：草稿只比主快 1.25×（同架构同参数量，速度差≈体积比），任何 n_max 下都无法回本——即使接受率 100%，n_max=8 的理论上限也只有 +8%；temp 0.8 下真实接受率 25%，倒亏 3.6×。0.6B 首发不默认开（与 §4.2 原判断一致，且有数据支撑）。
  **4B 仍是主战场**：4B Q4_K_M（~2.4GB）主 + 0.6B IQ4_XS（450MB）草稿速度差 ~5.3×，回本门槛 γ>0.19，实测接受率区间内可期 +80%~+130%（4B 上线时真机终裁）。

## 5. 天梯与情绪价值

- **内置天梯表（本地，零上传）**：随 App 版本发布，纯本地对比，不碰隐私卖点。
  数据结构（`benchmarkLadder.json` 打进 App 包）：

  ```json
  {
    "benchmarkVersion": "1",
    "formulaVersion": "1.0",
    "entries": [
      {"device": "iPhone 18 Pro Max", "ram": "12GB", "score": 91, "date": "2026-11-15"},
      {"device": "M5 Pro MacBook", "ram": "24GB", "score": 96, "date": "2026-11-15"}
    ]
  }
  ```

- **击败百分比**：由天梯分布本地算出（「你的设备击败了 87% 的入库设备」）。
- **分享卡片**：分数 + 机型 + 击败百分比 + 引擎版本，可截图分享。
- **云端实时排行榜（已拍板后置 V2）**：opt-in 才上传，且只传 `{机型, 分数, benchmarkVersion, formulaVersion}` 四个字段——**不含任何对话、prompt、个人信息**。V1 只做内置天梯。

## 6. 模块归属与目录

- `engine/Sources/EngineKit/BenchmarkKit/`（Swift，随 M2/M3 实现）：
  - `BenchmarkRunner`：跑基准负载，产出 tok/s 曲线
  - `ScoreCalculator`：纯函数算三子分 + 总分（可单测）
  - `DeviceLadderStore`：解析内置天梯 JSON、算击败百分比
  - `RecommendationEngine`：分数 → 档位 → 模型池 + 默认 SpeedTier
- **SDK 公开 API 草案**（第三方 App 集成后即拿到的能力）：

  ```swift
  // 第三方 App 只需三行调用，跑分/推荐/天梯全到手
  let result = try await engine.benchmark()   // 2 分钟标准负载
  // BenchmarkResult { score, tier, tokPerSecCurve, stability, memoryGB, beatPercent }
  let rec = RecommendationEngine.recommend(for: result)  // 模型池 + 默认 SpeedTier
  let ladder = try DeviceLadder.bundled()     // 内置天梯，本地对比零上传
  ```

- `apps/demo`：薄壳参考实现——首启向导页（内存快检 → 预估档位 → 推荐池 → 下载 → 下载后真实跑分）+「设备」页重测；所有逻辑调 SDK，不另写。

## 9. 真机测试风险备案（2026-10-25）

> 与测试相关的、可能在手机上出现的问题全部备案于此；实现期逐条转成 EngineKit 的守卫与测试纪律。状态分三类：已拍板（契约级）/待实测（真机数据说话）/待实现（M2 落地）。

### 9.1 内存

| 风险 | 现象 | 对策 | 状态 |
|---|---|---|---|
| iOS jetsam 无警告杀进程 | 跑分中途闪退、无报错 | 模型加载前 `os_proc_available_memory` 守卫；跑分中采样内存水位，逼近上限提前终止并判无效 | 待实现 |
| 后台 App 占用波动 | 同一设备两次跑分 M 分抖动 | 跑分前提示清理后台；M 取测量窗口内均值 | 待实测 |
| 三代真机 RAM 不同（16 Pro 8GB vs 17/18 Pro 12GB，待确认） | 基准模型在 8GB 机型装不下 | **基准 Q4_K_M + KV cache 必须在 16 Pro 实测装得下**，否则基准模型降档重选、分数全部重校准 | 待实测 |
| 投机采样双模型常驻（§4.2） | 8GB 机型内存吃紧 | 真机实测双模型 + KV 峰值水位，超预算则该档在低分设备禁用 | 待实测 |

### 9.2 热控

| 风险 | 现象 | 对策 | 状态 |
|---|---|---|---|
| 2 分钟持续推理发热降频 | tok/s 后半段下滑，T 分失真 | 契约已用 T 捕获降频；但**跑分前必须查 `thermalState` 为 nominal**，否则提示「设备过热，冷却后再测」 | 待实现 |
| thermalState 达 critical 被系统强杀 | 跑分中断 | 推理循环内监听热状态，critical 前主动中止判无效 | 待实现 |
| 充电 + 跑分双热源 | 分数偏低、触发限频 | 已拍板：允许但强制提示「充电发热可能导致分数偏低」；实测充电 vs 不充电的分数差，标注条件不佳 | 已拍板 |
| 环境温度/手机壳/高亮度/120Hz 屏幕 | 热基线不同，分数波动 | 跑分记录标注条件；冷却 5 分钟是否足够需三台真机实测校准 | 待实测 |

| 风险 | 现象 | 对策 | 状态 |
|---|---|---|---|

### 9.4 推理引擎

| 风险 | 现象 | 对策 | 状态 |
|---|---|---|---|
| Metal kernel 首次编译延迟（shader JIT） | 首次跑分偏慢，分数虚低 | 预热 10 秒是否够需真机实测；不够则延长预热或跑前执行一次短生成热 kernel | 待实测 |
| 旧芯片（16 Pro A18）对量化 kernel 支持/性能路径差异 | 某档速度异常低（疑似回退 CPU 或低效路径） | 三台真机必须全部跑基准负载；发现异常路径记录在案并反映到推荐与天梯标注 | 待实测 |

### 9.5 测量流程与可比性

| 风险 | 现象 | 对策 | 状态 |
|---|---|---|---|
| 同一设备重复跑分方差未知 | 天梯与击败百分比不可信 | 每台真机冷态重复 ≥3 次取中位数，报告方差；方差过大则加长测量窗口 | 待实测 |
| 电池健康度 <80% iOS 性能管理降频 | 分数永久偏低 | 跑分结果记录电池健康度，标注条件不佳 | 待实现 |
| 存储空间不足 | 模型下载失败/中断 | 下载前检查剩余空间，支持断点续传 | 待实现 |
| 跑分总时长（模型加载+预热+2 分钟） | 首启体验拖沓 | 首启允许跳过、跑分后置到「设备」页（已拍板） | 已拍板 |
| SDK 版本变化导致分数不可比 | 天梯分数打架 | 分数随 SDK 版本标注；SDK 升级重校准，天梯标注基准版本号 | 已拍板 |

### 9.6 校准数据采集规格

- 设备矩阵：iPhone 16 Pro / 17 Pro / 18 Pro（三代芯片）+ Mac（M5 Air / M5 Pro，双机）。
- 每台设备：冷态（thermalState = nominal）重复 ≥3 次基准负载，记录完整 tok/s 曲线、峰值 RSS、电池健康度、充电状态、环境条件。
- 产出：S/T/M 映射系数校准、分档阈值、天梯初始表、冷却时间定值。
