# SFT20b 工人日期补训（0.6B）

> 状态：2026-11-06 用户拍板「0.6B 日期可以补训一轮」。数据生成中，base=SFT20 工人 final。

## 1. 背景与目标

SFT20 工人（0.6B）评测 7/8，唯一系统性错误是周表达换算：「下周一」→ 2026-11-07（应 11-09）。训练集含「下周X」样本 72/72 全对，属 0.6B 容量不足、样本密度不够，不是数据脏。

目标：在不破坏现有工具调用格式与翻译/摘要能力的前提下，把相对日期（重点「下周X」）换算正确率拉到 90% 以上。

## 2. 数据设计（规则生成，零教师成本）

- 来源：`train/synthesize/gen_date_worker.py`，用 `datetime` 规则计算，目标日期 100% 可验证。
- 规模：日期样本 4000（日历 2400 / 提醒 1600）+ 回放 800（translate 300 / summary 300 / calendar 100 / reminder 100）= 4800（原计划回放 1000，worker_sft20 每类只有 300 条，实际 800）。
- 覆盖：
  - 相对：今天/明天/后天/大后天/N天后；
  - 周：这周X / 本周X / 下周X / 下下周X，X 覆盖周一至周日，基准日覆盖七个星期几；
  - 绝对：M月D日/号、下个月D号；
  - 时间：早上/上午/中午/下午/傍晚/晚上/凌晨 + 整点/半/一刻/三刻/X分；
  - 合并表达：今晚X点、明早X点、明晚X点；
  - 时长：15/30/45/60/90/120/150/180 分钟，20% 不写时长（默认 60）；
  - 边界：跨月、跨年、闰年 2 月 29 日、事件跨午夜。
- 周约定与 SFT20 数据一致：本周 = ISO 周（周一起），下周 = 下一个 ISO 周；本周只生成今天及之后的星期几。
- 回放：从 `cloud_sft20/worker_sft20.jsonl` 分层抽样，保持四种工具 schema 与翻译/摘要分布。

## 4. 评测门禁

60 题 held-out 日期集（与训练不重叠）：

- 日期 exact：start_time / end_time / remind_time 全对 ≥ 90%；
- 相对日期泄漏：0；
- JSON / schema：100%；
- 回归：SFT20 的 8 题 worker dispatch 集不降（≥7/8 且工具选择全对）。

**基线（2026-11-06，SFT20 工人 Q5_K_M）**：60 题 time_exact 16（26.7%）；下周X 0/22、这周X 1/8、相对 6/8、绝对 4/8、下个月 3/6、边界 2/8；emit 59/60、JSON/schema 59/60、相对泄漏 0。补训要解决的核心就是下周X。

训练后若门禁不过，回滚 = 继续用 `qwen3-0.6b-sft20-20261106`，本次输出目录保留可复查。

**失败模式**：模型把「下周X」当成「今天+7」，不会按星期几推算（如周五说「下周一」→ 11-07）。训练 loss 已到 0.01，是 0.6B 的算术容量问题，不是数据或拟合不足。

**零样本查表失败**：直接把「本周/下周/下下周」日期表追加到用户输入，SFT20b emit 1/60，输出把整段输入复读一遍。表格必须进训练分布。

**SFT20c（查表版，已完成）**：从 SFT20b final 继续训，4200 条日期样本带日期表；translate/summary 3 倍过采样（882/870）+ 200 条日历/提醒回放，共 5872 条，2 epochs / 184 步，14:14:24 完成，loss 0.0004。

**结论**：采用 SFT20c，日期表必须由引擎注入；剩余 4 个失败为闰日/跨年/小时进位边界。此前 SFT20/SFT20b 的回归失分是评测端没注入空思考块，补上后三版均 8/8。详见 `docs/评测/SFT20b-SFT20c-工人日期补训.md`。
