# 记忆赛道：精确空白清单（2026-11-10）

> 目标：找出「目前没有人做精」的点，不考虑实现难度。
> 方法：四路并行扫 arXiv / 顶会 / 开源项目，再对关键论文逐篇核摘要。核实等级：A＝读过摘要原文；B＝二手列表/报道；C＝未核实。
> 覆盖：MemGPT/Letta、Mem0、MemOS、MemoryOS、A-MEM、Zep、AgeMem、Memory-R1、Mem-T、MemSkill、UMA、EverMemOS、MemX、MemSifter、BudgetMem、PlanFence、MemClaw、Collaborative Memory、Agentsensus、TOKI、MemCut、AfterDeleteBench、MemPoison、GateMem、MemLeak、MobileMem、mzCache、MobileMem、MRAgent、Mi-Memory、CEG-Agent、AgentDebugX。

## 0. 先说结论

2026 年这条线的主战场已经从「怎么存、怎么检索」移到「怎么治理、怎么验证、怎么迁移」。存储和检索基本没有空白；**剩下的洞集中在四件事：维护、迁移、传播、评审**。

四个原本像空白、实际已被占的点（重要，避免撞车）：

| 原以为的空白 | 实际已有工作 | 核实 |
|---|---|---|
| 记忆的隔离级别/并发写 | TOKI：把矛盾消解定义为并发控制，四种算子各自声明隔离级别，输的一方留审计行 | A（arXiv 2606.06240） |
| 删除与残留 | MemCut（456 条秘密、residual recovery）；AfterDeleteBench（删后行为审计，溯源闭包可把恢复率打到 0） | A（2610.21405 / 2610.31366） |
| 团队共享记忆治理 | MemClaw/ArgusFleet：scoped retrieval + temporal supersession + provenance + 策略传播，含生产 negative results；Collaborative Memory：非对称时变 ACL + 不可变 provenance | A（2606.24535 / 2505.18279） |
| 检索准入/错误上下文 | NeurIPS 2026 Workshop《The Right Memory in the Wrong Context》专门验 retrieval admissibility | B |

## 1. 七个仍未被做精的点（按「洞的精确度」排序）

### G1. 记忆维护的预算调度（lifecycle maintenance scheduling）
- **缺口**：给定一堆记忆、各自的过期风险、核验成本、误用后果，**该在什么时候、花多少算力去复核/修复/丢弃哪几条**？没人把它做成一个带在线成本模型的调度问题。
- **最近工作**：BudgetMem（2602.06025，按 query 复杂度分配记忆处理预算，B）只解决「这一次查询花多少」；MemoRepair 自己问「维护值不值它的全部成本」，但 value/cost 是固定输入；PlanFence（2609.03340，A）只在动作前校验派生计划；Claude Memory 的公开设计也只说「定期全查太贵，值得测触发式复核」。
- **差的精确一步**：把「维护」当成可调度资源——用陈旧率、访问频率、动作不可逆性做优先级，给出 accuracy vs. 核验 token 的 Pareto 曲线。
- **为什么没人做**：benchmark 只测回答，不测维护；维护发生在离线，成本不进指标。
- **可检验问题**：注入会过期的记忆，预算从 0 到全量，比较 LRU/新近/随机/风险优先四种策略的「每千 token 核验换多少准确率」与「陈旧动作率」。
- **适合**：NeurIPS/ICLR 效率 track、ACL/EMNLP agent track、MLSys。

### G2. 端侧记忆的真实资源 Pareto
- **缺口**：记忆的抽取、嵌入、索引、合并、遗忘本身在手机上的**内存/延迟/热/电**四维联合曲线，没有公开数据。
- **最近工作**：mzCache（B）只报端侧推理的 TTFT；MemX（2603.16171，B）报检索延迟 90ms；MobileMem（B）只测记忆能力不测资源；RSM-full（2609.04915，B）在 4K 预算下做云端组装。
- **差的精确一步**：把记忆生命周期当负载，在真机上测策略 × 预算的 Pareto，而不是只测单次检索。
- **为什么没人做**：记忆 benchmark 在云端跑；移动系统论文只管 KV/权重，不管语义记忆。
- **可检验问题**：同一台 iPhone，四种策略（全量/向量 top-k/规则/小模型路由），4K 上下文，测准确率、首 token、峰值内存、能耗、机身温度。
- **适合**：MobiSys/MobiCom/ASPLOS/OSDI 的短文或 workshop；NeurIPS 效率 workshop。

### G3. 变更驱动的失效闭包（change-driven invalidation closure）
- **缺口**：删除之外的**变更**——代码、文档、模型、策略改了——如何沿依赖图把派生的摘要、图边、procedure、其他 agent 的副本标记失效，并决定「重建还是丢弃」。
- **最近工作**：AfterDeleteBench（A）只处理删除；PlanFence（A）只处理计划交接的 derivation currency；Concord（B）只连单 agent 上下文与文件；MemClaw（A）做 store 内的 temporal supersession。
- **差的精确一步**：general change 的传播闭包 + 选择性重建（rebuild vs. discard vs. re-derive），并把「一次 commit 影响哪些记忆」做成可查询的反向依赖。
- **为什么没人做**：删除 benchmark 才刚出现；变更传播需要类型化的依赖图和团队级 ownership，工程重、论文少。
- **可检验问题**：建一个带依赖类型的记忆库，改一条源；比较「无传播/全量失效/闭包失效」三种策略的陈旧答案率与重建成本。
- **适合**：OSDI/SOSP/ASPLOS（系统）、ACL/EMNLP（资源与评测）。

### G4. 矛盾记忆的条件化合成（conditional truth）
- **缺口**：两条记忆**在各自语境下都对**（项目 A 用 Redis、项目 B 不用；旧环境 apt、新环境 brew），现有系统只做「谁赢/留审计」，没人合成「在 X 条件下用 A，否则用 B」的条件记忆。
- **最近工作**：TOKI（A）做双时态算子与审计；LatticeMind（2608.08236，B）只分胜负；Agentsensus（A）只合同一事件；MELD（B）做分布式合并协议；CRDT（B）只保字符收敛。
- **差的精确一步**：把 scope/condition 变成记忆的一等字段，并评测「条件合成 vs. 最新优先 vs. 证据加权」在下游任务上的差异。
- **为什么没人做**：benchmark 把矛盾当错误，不把「分歧」当信息；LLM 冲突识别本身只有约 60% 准确率（二手）。
- **可检验问题**：构造「冲突但分属不同 scope」的偏好/流程集，测错误 scope 应用率与任务成功率。
- **适合**：ACL/EMNLP/NeurIPS。

### G5. 记忆投毒的传播半径（blast radius）
- **缺口**：一条毒记忆经过 N 轮 consolidation 后，污染多少派生摘要、图边、procedure、其他 agent、以及最终动作？没有「感染曲线」基准。
- **最近工作**：MemPoison（CCS 2026，2605.29960，B）测最终行为损坏率；Zombie Agents/sleeper poisoning（B）测触发；AfterDeleteBench（A）给了删除的级联，但没给投毒的级联。
- **差的精确一步**：纵向传播基准 + 隔离粒度（条目/主题/agent/租户）对 blast radius 的影响。
- **为什么没人做**：攻击论文看最终成功率，记忆论文看 QA，交叉处没人做纵向测量。
- **可检验问题**：注入 1 条毒记忆，跑 20 轮整合，测被污染派生条目比例、跨 agent 扩散率、隔离策略的抑制效果。
- **适合**：CCS/USENIX Security/S&P（安全）、NeurIPS D&B。

### G6. 模型/量化升级后的记忆可移植性
- **缺口**：换模型、换量化档（Q5↔Q4）、换推理后端之后，旧记忆还读得懂吗？现有唯一受控研究只有 48 条合成历史、两个 <10B 模型。
- **最近工作**：2609.05339（A，LinkedIn）：固定 schema 几乎无损（±0.0004），自由笔记 ±9.91/−13.28，RAG 混合嵌入只拿到 4.96/11.90 的收益；结论是「升级要做记忆兼容性测试、保留原文」。
- **差的精确一步**：端侧量化/后端切换的可移植性协议 + 迁移预算（哪些重嵌入、哪些重写、哪些丢弃），以及真实长历史数据。
- **为什么没人做**：模型升级被当基础设施，不当记忆语义问题；端侧换档是 2026 才常见。
- **可检验问题**：同一记忆库，1.7B Q5→Q4、1.7B→0.6B，测 KG/notes/RAG 三种表示的准确率与恢复成本。
- **适合**：MLSys、EMNLP、端侧 workshop。

### G7. 记忆 PR 的评审度量（偏 HCI/SE）
- **缺口**：记忆条目该不该像代码一样走「起草→评审→合并」？评审的误纳率/漏纳率、reviewer 负担、diff 粒度、责任归属，没有任何研究。
- **最近工作**：Tencent TeamAI-CLI 用 Git MR 管 Skill（B）；GitAgent 支持 branch+PR（B）；Entire 做 agent 协作 Git forge（B）；Copilot 可提交 PR approval（B）。全是产品模式，没有度量。
- **差的精确一步**：把记忆条目当 PR 对象，做 diff + 自动冲突提示 + reviewer 责任，并测「自动合并 vs. 人评审」的误纳/漏纳。
- **为什么没人做**：多数系统默认自动写入，评审被视为产品流程而非研究问题。
- **可检验问题**：3–5 人团队，记忆 PR 流中注入坏条目，测检出率、耗时、误纳率。
- **适合**：CSCW/CHI、ICSE/FSE。

## 2. 排序与建议

按「洞的精确度 + 现有工作距离」排：

1. **G3 变更失效闭包**——最像数据库/系统问题，现有工作只做了删除和计划两个特例，一般化没人做。
2. **G1 维护预算调度**——问题清楚、可度量，BudgetMem 只占了「单次查询预算」，生命周期调度还空着。
3. **G4 条件化矛盾合成**——概念最锋利，现有工作全在「谁赢」，没人做「都留下、带条件」。
4. **G2 端侧 Pareto**——数据空白最确定，但贡献偏测量。
5. **G6 记忆可移植**——已有直接前作，端侧量化是增量，适合做 follow-up 而不是首篇。
6. **G5 投毒传播**——安全口径，门槛在威胁模型设计。
7. **G7 记忆 PR**——偏 HCI/SE，需要真人实验。

如果目标是「首篇就能站住」，选 G3 或 G1；如果目标是「用手上的设备做别人做不了的」，选 G2 + G6 组合；如果目标是「概念新、好讲故事」，选 G4。
