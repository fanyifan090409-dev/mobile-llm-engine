## A2. 三个最高 ROI 的可植入件

### ① projectmem：把「重复犯错」变成任务
- **它做了什么**：把所有开发事件写成 append-only 纯文本日志，确定性投影成摘要；改文件前做 file-scoped precheck，返回该文件记录过的失败、未决 issue、churn（它叫 Memory-as-Governance）。
- **它的数据**：3,228 个事件 / 27 个项目；427 个已关闭 issue 里有 86 个在首次修复前至少失败过一次；1,500 事件日志分析从 42.0s 降到 79.3ms。
- **它自己承认的空位**：这些历史「只是可被提醒的候选，不是提醒真的避免了失败」；论文明确提出需要一个受控的 repeat-failure benchmark。
- **怎么植入**：把事件日志 schema 和 precheck 逻辑抽出来，换成你的 SQLite/Swift 实现；任务从「开发事件」换成「工具调用失败」（日历写错、日期算错、OCR 识别错）。
- **为什么值**：它同时给你任务、baseline、指标和一句可引用的「作者说还没做」。

### ② Memoir：把「记忆写入 × 前缀缓存」做成指标
- **它做了什么**：Git 式版本化记忆、语义路径、分支感知；README 明确提出「token rent」——每次小改记忆都会让整个前缀缓存失效。
- **为什么值**：云端有 prefix-cache 研究（如 2609.28870 讨论 LRU/驱逐），系统侧有 2606.06448 给记忆做七阶段 profiling，但**没有论文把「记忆写入策略」和「前缀缓存命中率/TTFT」放在一起测**，端侧更没有。
- **怎么植入**：在你的 prompt 组装里把记忆分成「稳定前缀（固定位置、少改）」和「易变后缀」，比较两种布局的 TTFT、缓存命中、峰值内存。
- **风险**：Memoir 本身没有论文，只能当工程参考，不能当学术引用。

### ③ OKF Agent Memory：最轻的双记忆 baseline
- **它做了什么**：推送层放规范/约束（≤400 token，固定在前），拉取层放语义记忆（BM25，<300µs）；渐进披露；纯 Go、零依赖。
- **为什么值**：端侧不需要向量库，BM25 + 结构化文件就够；400 token 的硬上限正好适配 4K 上下文；MIT。
- **怎么植入**：作为「规则 baseline」对照你的小模型路由，证明小模型是否真的比「固定前缀 + BM25」更好。这是审稿人最会问的 baseline。

## A3. 由此收敛出的论文题（比上一轮的 G1/G3 更具体）

**题目方向：缓存感知的端侧记忆调度（cache-aware memory scheduling on device）**

- **问题**：记忆写入/注入会改变 prompt 前缀，导致 KV 缓存失效、TTFT 上升；在手机上重建 KV 比云端更贵。现有工作分别研究记忆质量（LoCoMo/LongMemEval）、记忆系统成本（2606.06448）、前缀缓存驱逐（2609.28870），**没有把三者接起来**。
- **假设**：把记忆按「稳定性」分层（钉在前缀 vs 放后缀），并按缓存失效成本调度写入，能在不降准确率的前提下降低 TTFT 和峰值内存。
- **对照**：全量注入 / 向量 top-k / 规则（OKF 式）/ 小模型路由（MemSifter 缩到 0.6B）/ 缓存感知调度。
- **指标**：任务准确率、TTFT、前缀缓存命中率、峰值内存、注入 token。
- **任务**：用 projectmem 的「重复犯错」场景构造——同一类工具调用错误重复出现时，记忆是否让第二次不再犯。
- **相邻工作**：2606.06448（系统 profiling，必须引用）、2609.28870（前缀驱逐，必须引用）、Memoir（工程主张，非论文）、MemSifter（路由器 baseline）。
- **风险**：如果测出来「规则 + 稳定前缀」已经足够好，论文的主张要改成「小模型路由在端侧不划算」——这也是有效结论。

## A4. 论文线结论

- 最值得先做的是 **projectmem 式事件日志 + 重复犯错基准**，因为它是唯一「代码、任务、指标、空白声明」四件齐全的。
- 第二个是 **Memoir 式缓存感知指标**，它把你的引擎优势（4K、真机 TTFT）变成论文卖点。
- 不要直接把 MemOS/Mem0 的代码搬进来：Python、云假设、依赖重，和你 2GB 的端侧目标不匹配。

## B2. 推荐组合：一个「可验证性」包

把 2 + 3 + 4 合成一个 Demo 段落，比三个散点更有力：

1. 点「自检」→ 16/16 全绿；
2. 做一次日历写入 → 弹出确认框 → 写入后溯源卡显示「模型/参数/结果/时间/确认人」；
3. 问一道数学题 → 结果下面显示「代回验证：x=2 ✓，x=3 ✓」。

这三步对应评委三个疑问：**真的能跑吗、出错谁负责、答案对不对**。比再讲一遍 61.1 tok/s 有效。

## B3. 六周排期（不含论文）

- 第 1 周：接线 GBNF + 回归；确认 16/16 不掉。
- 第 2 周：自检按钮进 UI + 结果页；溯源卡字段补齐。
- 第 3 周：数学验算展示 + OCR 自检 + 注入防护；补回归用例。
- 第 4 周：拍视频用这三个镜头；数字核对。
- 第 5 周：全片演练 + 备用机；风险表更新。
- 第 6 周：缓冲，只修 bug，不加功能。

## B4. 验收口径

- 每个新增件必须有 1 条自动化用例，且计入 16/16 之外的新套件。
- GBNF 上线后，工具调用评测要重跑 40/40；若掉分，回滚 grammar。
- 自检按钮不得写真实日历/提醒；用 harness 的临时事件并自清理（现有 harness 已有该逻辑）。
- 缓存布局如果测不出 TTFT 改善，就从 Demo 里删掉，不要口播没数据的结论。
