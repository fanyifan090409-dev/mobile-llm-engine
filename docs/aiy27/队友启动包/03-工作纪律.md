# 03 · 工作纪律

> 来源：队长平时用的 `/vibecoding` 纪律（防屎山 8 条），针对「文档 + 测试」这类任务改写。
> 一句话：**宁可交得慢一点，也不要交一份说不清来源的东西。**

---

## 8 条

### 1. 先规划，再动手

接到任务先读完任务单和验收标准，用自己的话复述一遍再开始。
**没看懂就问到看懂，不要边猜边做。**

### 2. 一次只做一件事

一个 PR 只解决一个任务。别顺手改格式、别顺手补别的章节。
范围一变大，评审就看不出你到底做了什么。

### 3. 先读规则，再看材料

按 00 → 01 → 02 → 03 的顺序读。项目数据以 `01` 为准，比赛要求以 `00` 为准。
**任何和你印象冲突的地方，以这两份文件为准。**

### 4. 自检不过不提交

提交前问自己四句，四句都能答「是」才点 Create pull request：

1. 每个结论都能指到截图或原话吗？
2. 每个数字都能指到来源文件吗？
3. 验收标准逐条覆盖了吗？
4. 我能不看稿讲清这份东西吗？

### 5. 真实数据必须自己核

数字不许从别处抄、不许让智能体「估一个」。
找不到来源就写「无来源」，不要编。

### 6. 不擅自加东西

不新增依赖、不加没人要求的章节、不改别人目录、不顺手重构。
发现该加的东西：写进报告的「建议」一节，由队长决定。

### 7. 小步提交

一次改一个文件，改完就提交。出问题能一键回退。
别攒一大坨再一起交——出了错没人能定位到是哪一步。

### 8. 发现问题只记录，不顺手改

看到别的毛病（错别字、排版、别处的 bug），记进报告的「附带发现」，不要当场改。
顺手改是冲突和返工的最大来源。

---

## 5 条红线

1. **不编数据。** 没跑过的不写「通过」，没访谈的不写「用户说」。
2. **不假装已实现。** 规划中的功能必须写「规划中」。
3. **不替别人署名。** 谁做的写谁。
4. **不自己合并 PR。** 合并权只在队长手里。
5. **不绕过检查。** 不允许为了让检查通过而删掉检查、改小范围、改验收标准。

---

## 交付前最后一句

> 如果这份东西被贴到评委面前，我能不能站着把它讲完？

答不上来，就还没做完。
