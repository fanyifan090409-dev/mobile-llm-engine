# 01 · 项目介绍与真实数据

> 给队员和队员的智能体看。这份文件的目标只有一个：**任何人问起这个项目的任何一个数字，你都能答出来，并且指得出来源。**

---

## 1. 一句话

**口袋里的 Agent 实验室**：把 1.7B 的量化模型和一套工具执行层装进 iPhone，断网也能完成「理解一句话 → 调手机工具 → 把结果写进日历」的完整闭环，数据不出设备。

## 2. 它不是什么（先划清，避免说错）

| 常见误解 | 事实 |
|---|---|
| 自研模型 | 不是。**基于 Qwen3 继续训练**（0.6B / 1.7B / 4B），对外一律说「基于 Qwen3 继续训练」 |
| 云端服务 | 不是。推理全程在手机本地，飞行模式下可用；没有账号体系 |
| 通用聊天 App | 不是。核心是**工具调用闭环** + 移动端运行时，不是陪聊 |
| 多 Agent 平台 | **目前不是**。单 Agent 工具闭环已跑通；本地多 Agent 编排是规划项，PPT 里标的是「规划」 |

## 3. 技术构成

| 层 | 用什么 | 说明 |
|---|---|---|
| 推理底座 | llama.cpp（MIT，钉版本） | 只当黑盒推理核心，不改 C kernel |
| 引擎 | EngineKit（Swift Package） | 模型加载/释放、KV 管理、内存预算、按需分发 |
| 工具层 | ToolKit（白名单 + JSON schema） | 模型只能调白名单里的工具，参数过 schema 才执行 |
| 演示壳 | iOS App（SwiftUI） | 真机跑分、自检套件、双模型切换 |
| 模型 | GGUF 量化：Q4_K_M / Q5_K_M / Q8 | 按设备内存分档推荐 |
| 公式 OCR | Texo（AGPL-3.0）+ ONNX Runtime Mobile | 拍照识题，本机解码 |
| 语音 | sherpa-onnx | 本机识别，音频不上传 |

## 4. 已实现 vs 规划中

**已实现（可以现场演示）**

- 本地推理 + 飞行模式可用
- 四类工具：日历、提醒、翻译、摘要（白名单执行，写入前有人确认）
- 日期换算（「明天下午三点」「下周五」这类相对时间）
- CAS 数学工具：解方程、求导、求极限（math_eval）
- 公式 OCR：拍照 → 识别成 LaTeX → 解题
- 语音输入：说一句话直接下单
- 双模型切换：领队（大模型思考）+ 工人（小模型执行）

**规划中（不许说成已实现）**

- 本地多 Agent 编排（8GB / 12GB 内存预算与 OOM 门禁已设计，未落地）
- Android
- TestFlight 公开分发（外壳已具备，尚未真正发版）

## 6. 口径纪律（最容易被问倒的四个坑）

1. **15/15 和 58/60 不是同一套题。** 前者是改前的 15 题基线（全错），后者是补了日期表之后扩到 60 题的验收集。两个数放一起讲时，必须说清「改前 15 题全错；补日期表后把验收集扩到 60 题，58/60」。
2. **40/40 只针对 1.7B Q5/Q4。** 不要推广成「所有模型所有工具都 40/40」。
3. **31 道 FRQ 是失败实验，不是成功率。** 它用来说明「纯训练容量到顶」，不是拿来夸的。
4. **61.1 tok/s 是稳定解码，不是峰值。** 场景套件里是 42–79 tok/s 的区间。说峰值或说区间时要标出来。

## 7. 已知边界（主动说，别等人问）

- 1.7B 的复杂推理有限：多步推理、长链路规划会错
- 工具只覆盖日历 / 提醒 / 翻译 / 摘要四类
- 日期题 60 题里还错 2 题；数学 69 题里错 11 题
- OCR 在极端手写、低光下会识别错
- Android 没做；多 Agent 没做；TestFlight 没真正发版
