## 2. 分工原则

一句话：**队长负责「把它做出来」，两位队员负责「证明它对、证明别人用得起来」。**

- 引擎、训练、App 的技术主线由队长独立完成——这部分在仓库提交历史里一目了然，不做任何掩饰。
- 两位队员的贡献在**验证、文档、演示**三条线上，每一项都是仓库内真实提交，能指到具体 PR。
- 不安排任何「挂名」工作：不代提交、不代签名、不补造记录。
- 队员不需要会 git 命令行，也不需要写代码。全部协作在 GitHub 网页端完成，操作步骤见 [队友操作指南](队友操作指南.md)。

## 3. 协作流程

```
队长开 Issue（任务单）
      ↓
队员在网页端建分支，按任务单执行，把结果写成 md 文件提交
      ↓
队员发起 PR，附上证据（截图 / 原话记录 / 来源文件）
      ↓
队长 Review：逐条对验收标准，打回或批准
      ↓
Merge 到 main，PR 编号记入本文档第 6 节
```

硬规则：

1. **一人一个 PR，不合并提交。** 谁做的写谁的名字，Review 意见留在 PR 对话里。
2. **证据随 PR 走。** 测试结果必须附截图或原话记录；PPT 数字核对必须写明来源文件和具体位置。
3. **AI 起草的部分要在 PR 里说明。** 例如「表格格式与文案由智能体整理，测试结果由本人实测填写」。
4. **队长只做评审与合并，不替队员改内容。** 需要返工时打回，写清原因，由队员自己改。
5. **main 分支受保护**，必须经 PR 才能合入，保证每个改动都有评审痕迹。

## 4. 三人三智能体的协作方式

这是本项目协作方式的真实特点，也是可以讲清楚的方法论：

| 成员 | 智能体承担 | 人承担 |
|---|---|---|
| 队长 | 生成代码骨架、调试、批量数据处理、文档初稿 | 架构决策、模型训练判断、真机验收、最终发布 |
| 张曜阳 | 把零散的测试记录整理成规范表格、汇总失败模式、起草缺陷描述 | **亲自在真机上逐项执行测试**、判断哪一项算失败、确认复现步骤 |
| 薛亦湘 | 整理访谈记录、起草分镜脚本、生成核对表框架 | **亲自组织同学试用并记录原话**、判断脚本节奏、逐条核对数字来源 |

红线（写进每份任务单）：

- AI 不能代替人产生测试结果。没跑过的项不许填「通过」。
- AI 不能代替人产生用户反馈。没访谈过的人不许出现在记录里。
- AI 起草的任何内容，人必须逐句复核后才允许提交。
- 每个 PR 要能被本人在两分钟内讲清楚：做了什么、为什么这么做、证据在哪。

配套的四条机制（对齐 2026 年通行做法，调研见 [协作方式调研-2026](协作方式调研-2026.md)）：

1. **单一指令源**：三个人、三个智能体，共用同一份 [智能体协作守则](智能体协作守则.md)。不各自维护一套提示词，规则只改这一份。
2. **路径所有权**：队员只写 `docs/aiy27/qa/` 与 `docs/aiy27/demo/`，主线代码与其它文档归队长。一人一分支，避免并行改同一处。
3. **规格先行**：任务单就是规格，含目标、交付路径、验收标准、证据要求；没有验收标准的任务不派发。
4. **参与披露**：PR 必填「AI 参与说明」；由智能体起草比例较高的提交，在提交信息末尾加一行 `Assisted-by: <工具>`。披露不转移责任——提交人仍是唯一作者。

配套可视化：[团队工作流.html](团队工作流.html)，16:9 单文件网页，无外链依赖，可离线打开、直接截入 PPT 或答辩时全屏播放。

队员上手材料：[队友启动包/](队友启动包/README.md)，比赛要求、项目真实数据、工作流程、工作纪律四份，按 00→03 顺序读，再领任务单。
