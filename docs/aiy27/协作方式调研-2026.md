# 多人 + 智能体协作：2026 现状调研与取舍

> 日期：2026-11-10
> 目的：比赛要求提交协作方式记录。在定稿前先看当前 GitHub 上真正跑通的做法，避免自己发明一套不合时宜的流程。
> 结论先行：**三人三智能体不是非主流，恰恰是 2026 年最被认可的一种形态**——前提是有单一指令源、规格先行、PR 留痕、AI 参与披露。

---

## 一、已经形成共识的五件事

### 1. 规格驱动开发（Spec-Driven Development）

`github/spec-kit` 到 2026 年 11 月约 14.8 万 star，周增 4280；1.0.0 于 2026 年 8 月发布，命令体系与扩展机制成型。核心主张不是「让 AI 更聪明」，而是**先把「要做成什么样」写成仓库里可校验的文件，人和 AI 在这份文件上达成一致，再动代码**。OpenSpec 走 npm 包路线，去掉了阶段闸门。

教训：任务描述写在聊天记录里等于没写。任务必须有仓库内的落点，且带验收标准。

### 2. AGENTS.md 成为跨工具事实标准

由 OpenAI、Anthropic、Google 等推动，2025 年 12 月捐给 Linux 基金会下的 Agentic AI Foundation（AAIF）。截至 2026 年初超过 6 万个开源项目采用；2026 年 9 月抽样显示 6.2% 的 GitHub 活跃仓库含 AGENTS.md，高于 CLAUDE.md 的 5.4%。Claude Code 从 2026-09-19 起原生读取 AGENTS.md，跨工具双份维护的历史结束。

教训：**一个项目只维护一份写给智能体的说明书**。三个人用三种智能体时，这一份就是唯一事实源。

### 3. Issue → Agent → PR → 人评审，已经成为标准链路

GitHub 的做法是把 Issue 直接指派给 Copilot cloud agent，Agent 自主完成并开 PR、请求人工评审。2025-10 的 Agent HQ 统一管理多家 Agent；2026-10-28 Agentic Workflows 正式 GA（自然语言 Markdown 编译成 Actions YAML）；同期上线 Copilot Projects（跨仓库 Agent 舰队）与 Copilot Fusion（按任务类型路由模型）。

教训：**任务的载体是 Issue，产出的载体是 PR，人的位置是评审**。这条链路和用什么智能体无关，三个高中生的仓库照样跑得通。

### 4. 并行靠隔离，不靠自觉

2026 年下半年 `git worktree` 从冷门命令变成 AI 并行开发的基础设施：多个 Agent 各自一个工作目录、各自一个分支，互不覆盖。社区同时踩出教训——worktree 之间互相看不见对方改了什么，所以**隔离解决的是冲突，不解决一致性**，最终仍要靠 PR 合并与评审收敛。

教训：给每个人划**路径所有权**（这块目录只有你能改），比事后解冲突便宜得多。

### 5. AI 参与披露已经写进正规项目的规则

- OpenSSL 贡献指南：无论初稿出自谁（包括 AI），**你都是所提交内容的作者**；必须完整读过、亲自构建测试、能回答评审对任意一行的提问。使用 AI 时在提交信息加 `Assisted-by: <工具>:<模型>` 尾注。
- Linux 内核讨论中的提案要求 AI 助手用 `Co-developed-by` 标识自己。
- GNOME 给「主要或完全依赖 AI 生成」的 MR 加了 *Probabilistically Automated* 标签，理由写得很直白：这类提交常伴随**测试不足，以及按「听起来合理的预期行为」而不是代码正确性来写报告**。
- 工具层面出现 `git-ai` 这类做行级溯源的项目，把 AI 写的行关联到具体 agent、模型与 prompt。

教训：披露不会减分，隐瞒才会。GNOME 那句话尤其要贴在墙上——**「应该能跑」不是测试结果**。

## 二、三条直接对应到本项目的教训

| 问题 | 业界踩过的坑 | 我们的对策 |
|---|---|---|
| 三个人三个智能体，规则各说各话 | 多份规则文件不同步，AI 按过期版本干活 | 只保留一份 [智能体协作守则](智能体协作守则.md) 作为唯一指令源，三个智能体共用 |
| 智能体把「听起来对」写成「测过了」 | GNOME 标签指出的典型症状 | 每份任务单硬性要求实测证据；PR 评审逐条对证据，不看结论看截图 |
| 并行改同一处导致冲突 | worktree 隔离了文件，但隔不开决策 | 按目录划分所有权：队员只写 `docs/aiy27/qa/` 与 `docs/aiy27/demo/`，主线代码归队长 |

## 三、采纳与不采纳

**采纳**

- 规格先行：每份任务单即规格，含目标、非目标、交付路径、验收标准、证据要求。
- 单一指令源：三人三智能体共用 `docs/aiy27/智能体协作守则.md`。
- Issue → PR → 评审 → 合并，main 分支保护。
- 路径所有权 + 一人一分支，等价于 worktree 的隔离效果，但在网页端就能完成。
- AI 参与披露：PR 必填「AI 参与说明」，重要提交附 `Assisted-by` 尾注。
- 作者责任：能解释每一行，答不上来就重做。

**不采纳**

- 多智能体编排框架（CrewAI、AutoGen 一类）：三人规模用不上，引入即负债。
- worktree / 多开会话并行：这是单人驱动多 Agent 的解法，我们的并行度来自三个人本身。
- Agent HQ、Copilot Projects、Agentic Workflows：面向团队规模化与跨仓库舰队，比赛规模没有收益，且需要付费许可。
- 让 AI 做最终评审：AI 可以预审格式与漏项，但合并权必须在人手里，否则记录失去意义。

## 四、对比赛的用法

一句话可讲：**三个人、三个智能体、一份共同守则、每个产出都经 PR 评审合并。**

这句话之所以站得住，是因为它对应的是 2026 年业界正在收敛的做法——规格先行、AGENTS.md 单一指令源、Agent 产出走 PR、AI 参与如实披露。评委问「你们怎么协作」，答的是流程和证据；问「AI 做了多少」，答的是人负责判断与验收。两句都不需要夸张。
