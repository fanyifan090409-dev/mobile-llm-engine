## 第一部分：分镜脚本

### 硬约束

- 总时长 **≤ 8:00**（含片头片尾），留 20 秒余量，目标 7:40
- 必须**真机实拍**：iPhone 屏幕录制 + 手机实拍画面，不能全是录屏
- 核心流程必须**飞行模式下**连续一次拍完，不允许剪接拼接冒充连续操作
- 至少一个镜头展示「不联网也能用」（开飞行模式的画面必须在成片里）
- 结尾必须有 GitHub 仓库地址

### 形式已定（2026-11-10，队长拍板）

**混合制：真人出镜做叙事主线，真机录屏做演示主体。不做全程真人跟拍，也不做纯录屏配音。**

| 形式 | 占比 | 用在哪 |
|---|---|---|
| 真人出镜（正脸或半身） | 约 25% | 开场、每个能力的转场一句话、团队段、结尾 |
| 真机屏幕录制 | 约 55% | 核心闭环、数学/OCR、确认弹窗 |
| 手机实拍（手部操作 + 飞行模式图标） | 约 10% | 证明是真机，不是模拟器 |
| 标题卡 / PPT 图表 | 约 10% | 跑分、回归数据 |

拍摄与制作规则：

- 两台手机：一台演示并开系统录屏，另一台架支架拍手部/桌面全景，两路同时开录，后期对齐
- 真人镜头用第三台手机横屏拍（或第二台拍完再拍人），自然光、纯色墙、不美颜不滤镜
- 音频用有线耳机麦或领夹麦，**不要 AI 配音**；三人各录自己的段落，薛亦湘可远程录
- 剪映专业版剪辑，1080p / 16:9 / 30fps；字幕硬烧（评委可能静音看）
- 推理过程不加速；确需加速的镜头在字幕标「2×」
- 分镜按段落独立拍摄，某段失败只重录该段；但核心闭环那一段必须一条过，失败就重拍整段
- 失败镜头不靠剪辑假装成功：要么保留并解释，要么重拍，不允许拼接伪装

分工与排期：

- 樊一凡：主讲 + 操作 + 提供演示机；12-05 前确认脚本，12-08 拍完素材
- 薛亦湘：分镜、拍摄、剪辑、字幕、数字核对；12-12 粗剪，12-15 定稿
- 张曜阳：出镜 15-20 秒讲首次安装卡点，提供 T1 的真实截图/录像
- 12-20 全片演练并检查备份；成片和原始素材各存两份（硬盘 + 异地）

### 结构（已定，单段可微调 ±10 秒但要说明理由）

| 段落 | 时长 | 内容 | 形式 |
|---|---|---|---|
| 开场 | 0:00–0:25 | 痛点一句：数据不敢传、断网就用不了；我是谁、我们三个人 | 真人出镜 |
| 产品定义 | 0:25–1:05 | 一台 iPhone 跑完整闭环，不联网，数据不出设备 | 真人 + 界面 |
| 核心闭环 | 1:05–4:05 | 飞行模式下连续一次：语音下单 → 提醒真的写入 → 回读验证 → 断网数学题 | 录屏 + 手部实拍 |
| 能力与拦截 | 4:05–5:25 | 拍照识题；故意说「昨天三点提醒我」，展示过期时间警告和确认弹窗；拒权限后的降级提示 | 录屏 |
| 工程深度 | 5:25–6:25 | 61.1 tok/s、1.90 GB、16/16 回归，口播数字并标条件 | 图表 |
| 团队与协作 | 6:25–7:05 | 三人各 10-15 秒：张曜阳讲首装卡点、薛亦湘讲用户测试、樊一凡讲评审合并；配 Issue/PR 截图 | 真人 |
| 收尾 | 7:05–7:40 | 明说限制（多 Agent/Android 没做）、仓库地址、下一步 | 真人出镜 |

### 每个镜头必须写清

```markdown
### 镜头 03 · 飞行模式下单
- 时间：1:20–1:55
- 画面：手机实拍，从控制中心打开飞行模式，再切到 App
- 操作：说「明天下午三点提醒我交作业」
- 旁白：「全程没有网络。模型在手机里，日历工具也在手机里。」
- 预期结果：日历里出现 15:00 的事件
- 失败预案：如果没写入，改成口播「这一步在 16/16 回归里是通过的，现场这次超时了」并继续，不要重录掩盖
- 拍摄要点：飞行模式图标要清晰可见
```

### 验收标准

- [ ] 每个镜头都有时间码、画面、操作、旁白、预期结果、失败预案六项
- [ ] 总时长加起来 ≤ 8:00，且标注了余量
- [ ] 有明确的拍摄顺序与设备清单（几台手机、要不要支架、光线要求）
- [ ] 核心流程标了「一次拍完，不许剪」
- [ ] 至少 2 个镜头有备选拍法（万一当场失败）

## 第二部分：数字核对表

### 方法

1. 打开 `docs/aiy27/AIY27-PPT-v6.pptx`，逐页找数字（跑分、百分比、题数、内存、耗时、许可证年限等全部算）。
2. 每个数字去仓库里找来源，填进表里。常见来源位置：
   - `docs/评测/` 下的评测报告
   - `train/lab-notebook/训练线总览.md`
   - `docs/plans/多模态输入-v1.md`（回归结果）
   - `docs/plans/演示壳Harness化-v1.md`（真机自检）
   - `docs/aiy27/PPT-v6-产品发布级重做.md` 的数字口径小节
3. 找不到来源的标「**无来源**」，不要自己猜一个。
4. 找到但和 PPT 不一致的标「**不一致**」，写清实际值和差值。

### 表格格式

```markdown
| PPT 页 | 数字 | 上下文 | 来源文件 | 具体位置 | 结论 |
|---|---|---|---|---|---|
| P1 | 61.1 tok/s | 18 Pro Max · 1.7B Q4 | docs/评测/xxx.md | 「真机跑分」表第 2 行 | 一致 |
| P8 | 58/60 | 日期题 | train/lab-notebook/训练线总览.md | 2026-11-08 行 | 一致 |
| P5 | 96.7% | 60 题日期集 | 同上 | 同上 | 一致（58/60=96.67%） |
| P4 | 1.90 GB | 峰值内存 | — | — | 无来源 |
```

### 验收标准

- [ ] PPT 十页里出现的**所有**阿拉伯数字都被收录（页码、年份、许可证名称里的数字除外，但要单独说明排除了哪些）
- [ ] 每个「一致」的结论都能指到文件的具体位置（章节名或表格行）
- [ ] 「无来源」「不一致」的项单独列成一节，写清建议怎么处理
- [ ] 百分比类数字自己复算一遍（例如 58/60 是不是 96.7%）

---

## 必须附带的证据

- [ ] 核对表里每条来源的位置必须精确到「文件 + 章节/表格行」，不能只写文件名
- [ ] 分镜脚本里的时长是自己掐表算过的（可以说怎么算的）

## 禁止事项

- [ ] 数字直接从 PPT 抄到「来源」列
- [ ] 找不到来源就写「应该没问题」
- [ ] 分镜脚本写成「大概拍一下产品就行」这种没法执行的描述
- [ ] 让智能体编造原话或来源位置

## 可以交给智能体做的部分

- 帮你算百分比和时长总和
